# JARVIS Android 2T Inference Contract

## Purpose

This document defines how the Android application uses a future JARVIS 2T sparse-MoE model without placing the model weights or model authority inside the APK.

## Runtime

1. The verified local llama.cpp model is the offline fallback.
2. When explicitly enabled, Android sends the prompt to an authorized HTTPS OpenAI-compatible inference endpoint.
3. The endpoint may be backed by vLLM or another compatible distributed inference runtime.
4. The remote model returns text or structured tool intent.
5. Android executes tools only through ToolDispatcher and its capability/policy/permission/authorization pipeline.

vLLM currently documents an OpenAI-compatible /v1/chat/completions endpoint and current tool-related request fields. The JARVIS client intentionally keeps Android execution authoritative even when remote inference is enabled.

## Configuration

Remote inference is disabled by default.

Required fields: remote_enabled, remote_base_url, remote_model, remote_timeout_ms.

The endpoint must use HTTPS. Credentials are deliberately not stored in repository configuration.

## Failure behavior

Remote request failure, timeout, malformed JSON, or empty output falls back to the verified local model.

The Android app never treats remote model output as an instruction that can bypass Android permissions, ToolDispatcher validation, SecurityPolicy, confirmation, biometric/device-credential unlock, network policy, rate limits, audit logging, or the kill switch.

## 2T weights

A 2T checkpoint is not bundled in the APK and is not generated by Gradle.

The 2T model remains an external distributed inference asset. Exact checkpoint revision, format, tokenizer, runtime, and integrity information are required before a production endpoint is accepted.

## Training boundary

Runtime memory and lessons are not model-weight updates.

Runtime learning: execution -> outcome -> lesson -> validated memory -> future planning.

Weight learning: curated outcomes -> dataset -> training -> evaluation -> checkpoint audit -> deployment.

A checkpoint must pass architecture, parameter-count, tensor-shape, tokenizer, numerical-stability, security, and regression checks before deployment.
